Why long outages hurt the GRU forecaster

When readings are missing in long blocks, the GRU uses old filled values as if they were new. The information it needs is still in the input window. So most of the extra error is a failure of the model, not a loss of information.

1. The problem

Six sensors give one reading per time step. A model reads the last 24 steps of all six sensors. It then predicts sensor 0 six steps later. Some readings are missing. Before the model sees the data, each missing reading is replaced by the last known value of that sensor. This is called forward fill.

Window
The 24 past steps that the model reads for one forecast.
Forecast origin
The last step of the window. The forecast starts here.
Age
How many steps ago a sensor gave its last real reading. Age 0 means a fresh reading.
GRU
The small recurrent neural network (8 units) from the course starter.
Persistence
A simple baseline that repeats the last value of sensor 0.
MSE, RMSE
Mean squared error and its square root. Lower is better.

The course data removes 25% of readings in two ways. The scatter mask removes single readings at random. The block mask removes runs of 8 steps. Both remove the same number of readings per sensor.

The GRU is trained with the scatter mask. On the block mask its error goes up in every seed. Persistence also gets worse. The question of this step: why does the same amount of missing data hurt more when it comes in blocks?

The Kalman filter line is explained in section 3. Seed 942 has about 3 times the error scale of the other seeds, so its bars are longer.

2. Four possible explanations

We wrote down four explanations before we ran any experiment. For each one, we also wrote the result that proves it wrong. These are fixed in research/HYPOTHESES.md.

H1 · the given idea

Stale value at the origin

A block that ends at the origin leaves an old value in the last step. The model reads it as a new value.

Wrong if: the error gap is the same when sensor 0 is fresh.

H2

Lost history

Any 8-step hole in the window damages the memory of the GRU, wherever the hole is.

Wrong if: a hole far from the origin costs no error.

H3

Never seen in training

Scatter training almost never shows old values. So the GRU never learned to trust them less.

Wrong if: the best possible model loses as much as the GRU, or block training does not help.

H4

No help from other sensors

All sensors share the same hidden factors. When sensor 0 is old, the GRU does not use the fresh sensors instead.

Wrong if: outages on the other sensors matter as much as outages on sensor 0.

3. Experiments and why we chose them

Two tools make the experiments fair.

  • A Kalman filter as a measuring stick. The data comes from a known linear model. We recovered its exact parameters from the data generator. A Kalman filter with these parameters gives the best possible forecast from the same 24 steps. If the Kalman filter also loses accuracy under blocks, information is really lost. If only the GRU loses, the model is the problem. The Kalman filter is a tool for measurement, not a competing method.
  • Paired windows. Every model and every mask is scored on the same windows and the same targets. A mask only removes inputs. So a difference between masks cannot come from easier or harder windows.

Each result uses 3 data seeds (940, 941, 942) and 5 GRU starts per seed. The seed is the unit of replication. We report each seed, not only the mean. Only dev data was used. The test data was never loaded.

4. Results

Main result: the information is still there

The orange part is the gap of the Kalman filter. This is the information that the block mask really removes. The blue part is the extra gap of the GRU. It is 52% to 90% of the total, in 3 of 3 seeds. So the GRU loses accuracy that a better model keeps.

H1: old values at the origin start the problem Trigger, not cause

The block mask makes sensor 0 old at the origin in about 1 in 5 windows. The scatter mask does this in about 1 in 50.

On the same windows, persistence loses nothing when sensor 0 is fresh. The GRU loses most there too. But at age 5 and more, the Kalman filter loses several times less on the same windows (3 of 3 seeds). So the old value starts the problem, but the GRU makes it much worse.

The x axis is not to scale. Ages 1 to 4 have only 11 to 45 windows per seed, so those points are noisy. The old-value windows come from only 21 to 23 different outages per seed. E2 below is the cleaner test.

H2: lost history does not matter Rejected

We moved one 8-step outage through each window. An outage that ends 8 or 16 steps before the origin costs every model about 0 (3 of 3 seeds). Only an outage that reaches the origin costs error. On sensor 0, it costs the GRU 0.049 to 0.163 MSE and the Kalman filter only 0.001 to 0.010.

The x axis is not to scale. Seed 942 dominates the mean. See the per-seed tables at the end.

H3: the GRU does not learn to trust old values less Half right

H3 is right that the problem is in the model. But training on block masks with the same budget does not fix it. It removes the gap fully in only 1 seed (941) and partly in 1 seed (942).

The next chart shows the reason. We changed the last real sensor-0 value by a small amount and measured how much the forecast moved. The best forecast trusts a value less as it gets older. The GRU trusts old values the same or more. Block training lowers the curve, but the curve stays flat. Only 4 times more training with 32 units makes it bend down a little at high age. The age input changes the block RMSE by at most 0.0003, so the GRU does not use it.

H4: old values on other sensors also hurt Holds, wider than expected

We gave block outages only to sensor 0, only to the 5 other sensors, or to all. For the GRU, both parts cost error. Each part alone costs 31% to 67% of the full GRU gap. For the Kalman filter, each part costs less than for the GRU, in 3 of 3 seeds. Sensor-0 outages alone cost the Kalman filter almost nothing. So the GRU trusts the old filled value of every sensor, not only of sensor 0. This is wider than H4 expected.

5. Conclusion

Mechanism: stale-fill trust. Forward fill makes an outage look like a normal, constant reading. The GRU uses this filled value with the same weight as a fresh value. The best forecast gives it less weight as it gets older.

Scatter training almost never shows values older than 2 steps, so the GRU never needed this rule. The age information is in the input, but this small GRU does not turn it into a discount at this training budget. Block training at the same budget does not change that.

Limits

  • The data is synthetic: 6 sensors from 5 shared linear factors. Real sensors with nonlinear behavior were not tested.
  • Only the 8-unit starter GRU was tested, and one larger version (32 units, 4 times more training).
  • Three data seeds. The old-value results rest on about 21 to 23 outages per seed.
  • The Kalman filter knows the true model. It shows that the information is in the window. It does not show that a learned model can reach its error.

6. Next steps

  1. Step 2: prove the mechanism directly Keep the age of the old value the same and change only the value. Replace it with the Kalman estimate. If the extra GRU error goes away, stale-fill trust is confirmed. If it stays, the memory of the GRU is the problem.
  2. Step 3: one targeted change to the model Multiply each filled value by a learned decay, (fill − mean) · exp(−γj · agej). This is the input decay of GRU-D (Che et al. 2018), so the module itself is known. The new part is the test: with the same budget, does the trust curve go down with age, and does the old-value error drop?
  3. Step 3 alternative: a reliability score Predict the extra error of each window from how much the forecast depends on each value and how old that value is. Check on dev data if it finds bad windows better than the sensor-0 age alone.
  4. A limit that already holds On this data, the scatter-trained GRU is not reliable when any sensor is 3 or more steps old at the origin. Persistence is reliable only when sensor 0 is fresh.
  5. Freeze, then run the final test once Freeze the claim, the method and all settings. Then run --final one time. Also score scatter and block masks on the test period, so the effect of the new time period and the effect of the mask stay separate.
